# 单位机制收敛改造——来龙去脉

> 对象：Aspen Plus MCP（`D:\mcp-servers\aspen-mcp`）· 时间：2026-08 ~ 2026-09 · 提交：`5e8bef5`

## 一、起因

Aspen Plus 的 COM 自动化接口中，温度、压力、流量等数值都带单位，而单位体系会随用户在 Aspen 界面里切换全局单位集（ENG 英制 / SI 国际制）而变化。历次开发中单位机制反复出错：同样的值时而读成摄氏度、时而读成开尔文；代码为应对混乱不断堆叠"记住节点单位、读取时查表换算"的缓存机制，缓存一过期就静默算错，且多个排查结论互相矛盾。用户遂要求彻底调查、统一改造。

## 二、调查：真机实验摸清真相模型

在 Aspen Plus V15 41.0 自动化实例上跑了实验矩阵，结论如下（这是全部改造的依据）：

1. **`node.Value` 是不可信的**——它只是"最后一次输入的裸数字"，不随单位集切换重算（写 40°C 后 `Value=40`，但 `UnitString` 可能仍是 'F'）。读 `Value` + 判断单位字符串的做法必然错配，是历次混乱的根源。
2. **Aspen 原生就有正确的单位 API**：读用 `node.ValueForUnit(单位行, 单位列)` 绝对读取，写用 `node.SetValueAndUnit(值, 单位列)` 按单位解释写入、内部自动归一化。单位坐标是固定表（温度 row22 的 K/F/C、压力 row20 的 Pa/bar/kPa 等，SI 列恒为 col=1）。
3. **切换全局单位集（INSET/OUTSET）直接赋值即可**：`node.Value = "SI"` 一行生效；旧代码的"枚举子节点选中"法子节点访问直接抛 COM 2010 错误，是错的。
4. **节点一经写入，其单位即"定死"**——之后切换单位集，已写入值会正确换算、物理量不变。
5. **流股枚举节点（Input\TEMP 等）写入必须走 `node.Elements(0)`**，直接赋值报欠定错误。

方案演进：最初的方案 B（用 AttributeValue 统一读写）在实验中暴露语义错误，被证伪后修正为方案 B'——**统一走原生单位 API 读写**。

## 三、改造内容

- **`tools/units.py`（核心重写）**：以坐标表 + `read_si()`（一律按 SI 列绝对读取）和 `write_value()`（有坐标走 `SetValueAndUnit`，无坐标走 Python 换算表兜底写 SI）为统一进出口；**删除整个 UnitString 缓存机制**；旧转换函数保留为兼容层。
- **桥接层与工具层**（`bridge/windows.py`、`tools/{streams,blocks,paths,components,simulation}.py`）：删除所有"先换算再写入"的 pre-convert 代码，`unit` 参数一路直达原生写入；`get_value` 新增 `"si"` 视图（与界面单位无关的读取）；`set_unit_set` 改为直接赋值法。

## 四、验证

- 单元测试四个套件共 **78/78** 绿（test_units 54、test_bugfix_units 13、test_unitset_switch 5、test_attrvalue_diag 6），compileall 通过。
- 真机端到端 **15/15** 通过且三轮跑通（幂等确认）：写 40°C 读回 313.15 K、1 bar→100000 Pa、212°F→373.15 K、10 kW→10000 W、100 kmol/hr→0.027778 kmol/s；**切换 METCBAR 单位集后 SI 读值不变（旧机制的崩溃点，本次修复）**。
